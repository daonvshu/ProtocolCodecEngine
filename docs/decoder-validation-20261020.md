# 解帧兼容性与性能验证报告

验证日期：2026-10-20。

## 结论

本次执行的 21,988 组差异测试和四个旧版缺陷复现用例通过验收。除已证实的旧版缺陷外，
已测试输入下的回调内容、类型、顺序和每次输入后的回调进度与原版一致。
有 5,675 组分包用例触发旧版丢帧或选错帧缺陷；新版结果经过原版整包输入结果和预期帧数量核对，
按允许修复的差异记录，不能把这些用例描述为两版完全相同。

生成了两份各不少于 100 MiB 的测试数据。关闭日志时，四组测试中新版/原版中位耗时比为
0.991～1.016，均满足预先设定的“不超过原版 15%”验收线。
开启全部解析错误日志并实际写文件时，25、50、100 MiB 的中位耗时分别为
475.780、945.524、1898.450 ms；数据翻倍的耗时比为 1.987 和 2.008。
本次固定帧分布下表现接近线性，没有观察到耗时随数据量翻倍而加速膨胀。

这是一份有限场景的桌面离线验证结果，不等同于所有可能字节流的数学证明，也不等同于
ARM 板上的硬实时停止响应保证。

## 基准与可重复性

- 原版固定为提交 `600075a8bf33f3e1d252b2823881875b761ac803`，即本次修改前的工作树基准。
- `test/comparison/baseline.cmake` 从该 Git 对象提取原始源码到现有构建目录，
  只替换命名空间以隔离符号，不修改原版解帧、缓存、校验或编码逻辑。
- 原版和新版在同一个离线比较程序中运行，采用相同编译配置、Qt、输入数据、分块和回调统计逻辑。
- 环境为 Windows x64、MSVC Release（`/O2 /Ob2 /DNDEBUG`）、Qt 5.15.2。
- 使用已有 Release 构建配置，没有清理、强制重建或创建另一套构建环境。
- 随机数据使用固定种子 `0x63e27a91` 的确定性生成器。
- 性能测试每项运行三轮，交替先运行原版/新版，采用各自三轮耗时的中位数。
- 数据生成、保存、SHA-256 计算、解码器初始化和输入分块分配不计入解帧耗时；
  实际回调及内容摘要计算计入，双方完全相同。元数据记录关闭。

原始结果保存在 `docs/validation/decoder-20261020/`，包括比较统计、性能统计和四个独立缺陷复现结果。
大数据及完整诊断日志保留在 `<RELEASE_BUILD>/test/comparison-results/`，不纳入版本管理。

## 正确性测试

每次输入后比较双方已经产生的全部回调，包括类型、原始内容、数量和顺序。
元数据开启场景在回调发生时记录并比较成功帧元数据，避免拿后续不完整候选帧的元数据冒充成功帧信息。

| 空命令全部分包组合 | 128 | 8 字节手轮命令全部 `2^7` 种分包方式 |

### 允许的原版缺陷修复差异

1. **长度字段前或内部切分导致旧版丢帧。** 原版在 Size 校验返回 false 时移除已经匹配的帧头，
   即使原因只是长度字段尚未收齐，随后可能只保留帧头长度的后缀而丢失真实帧头。
   独立复现：一帧前四字节先到，其余内容连同下一帧后到；原版只回调一帧，新版正确回调两帧。
   相关差异不是任意放行：新版输出必须逐字节符合原版对同一数据整包输入的结果；
   普通差异只允许原版缺少回调，另外仅对两个明确的外层长度字段切分位置允许原版选错内层帧。
2. **按类型获取内容长度可能死循环。** 内容前面有地址等字段时，原版向前查找 Type 的循环未移动指针。
   原版独立子进程在 1.5 秒期限内不返回；新版正确返回一帧。只终止测试自行创建的子进程。
3. **Content 是最后字段时漏交付内容。** 原版提取类型和内容时不访问链表末节点，回调内容为空；
   新版交付预期的八字节内容。
4. **Size=0 与参与长度计算的 Type 矛盾时仍接受。** 使用独立 CRC 计算构造其他检查均合法的输入，
   原版回调一次，新版拒绝该非法长度且不回调。

上述四项分别有 `bug-*.json` 结果，原版失败、新版通过。CRC 打印指针地址的修复另由既有回归测试验证。

### 保持的原版重新同步策略

外层长度宣称还有后续数据，但缓存内部已经出现另一条完整有效帧时，继续搜索后续帧头的行为仍与原版一致。
这有助于从损坏长度中尽快恢复，但也存在协议歧义：未收齐的合法外层帧，其负载可以恰好包含完整合法内层帧。
本次不另行改变这项策略。若要求外层帧优先，需要另行确定等待上限/超时规则，并接受损坏长度后的恢复延迟变化。

### 性能分块为何按记录边界对齐

初次使用任意 64 字节切分时，100 MiB 正常流再次复现旧版长度字段分包丢帧，双方回调摘要不同。
继续比较耗时会让旧版以少处理部分帧的方式获得不公平优势，因此正式计时将输入结束位置对齐到生成记录的末尾。
两版仍使用完全相同的输入分块，且验证全部回调内容摘要和数量相同。

64 字节预算实际每次输入一个 74 字节帧；包含前置噪声的记录为 81 字节。
64 KiB 预算实际每次输入约 64 KiB，向后对齐至下一记录边界。
任意分包的正确性另由前述差异测试覆盖；此性能结果不宣称覆盖一字节输入等所有分块下的吞吐。

### 开启日志并写文件的增长趋势

使用混合错误数据前 25/50/100 MiB，开启 All 枚举，按约 64 KiB 输入。
Qt 消息处理器把完整诊断文本转换为 UTF-8 并写入真实文件，每轮末尾执行 `QFile::flush()`。
这包含解析、格式化、日志处理器及文件写入成本，但不包含强制物理存储同步。

| 输入 | 三轮中位耗时 ms | 比前一档耗时 | 日志条数 | 日志字节数 |
| --- | ---: | ---: | ---: | ---: |
| 25 MiB | 475.780 | — | 21,993 | 5,248,596 |
| 50 MiB | 945.524 | 1.987 倍 | 44,012 | 10,625,596 |
| 100 MiB | 1898.450 | 2.008 倍 | 88,033 | 21,204,966 |

约 1601 ms 增加约 19%；这不是所有磁盘和所有日志处理器的通用成本上限。

## 复现入口与结果位置

在已有 Release 构建配置中编译 `protocol_decoder_comparison` 和 `protocol_codec_engine_test`。
需要本地 Git 对象中保留上述固定基准提交；基准提取不会使用当前工作树内容。
运行 Qt 程序前，将该构建配置对应的 `<QT_BIN>` 放入 PATH；本次使用项目既定验证包装器执行。

在 `<RELEASE_BUILD>/test` 下运行：

```text
protocol_decoder_comparison --correctness
protocol_decoder_comparison --performance
protocol_codec_engine_test --decode-error-tests
```

成功标记分别为 `CORRECTNESS_RESULT passed`、`PERFORMANCE_RESULT passed`，进程退出码为 0。
结果位于 `comparison-results/`；常规回归详细结果为 `decode-error-functional.txt`、`decode-error-endian.txt`。

## 时效性边界

计时使用单调时钟，但桌面调度会带来抖动。无日志测试观测到的最大单次调用墙钟耗时为
33.954 ms，不能据此推导 MCU/ARM 上的最坏响应保证，也不能把中位吞吐当作最大延迟。
本次没有修改原有基于接收间隔、在下一批数据到达时检查的解码超时语义。

日志仍同步交给调用方的 Qt 日志处理器，慢磁盘、阻塞处理器和极高错误率仍可能延长接收线程占用。
本次 25/50/100 MiB 测试证明的是给定固定分布下的实测增长趋势，没有证明任意恶意流或
不断增长且逐字节追加的巨大不完整帧都具备线性复杂度。

未执行板端串口扰动、驱动层丢字节、实际停止请求端到端延迟、地址消毒器或长期内存压力验证。
框架源码和离线测试已更新，尚未替换设备使用的库或部署应用，也未创建 Git 提交。
